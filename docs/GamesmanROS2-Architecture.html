Rebuilding GamesmanROS
on ROS 2

An architecture rewrite that replaces a blocking monolith with a lifecycle-managed node graph — fixing the motion planning, gripper, and recovery failures that made the original system unreliable.
ROS 2 Humble · MoveIt 2 / OMPL · OpenCV · MyCobot 280 Pi
Status: 7 nodes implemented · pre-hardware-validation

Where we started

Three failures that weren't bugs — they were architecture

Failure 01

Motion planning

set_planner_id("LIN") forced every move onto a straight Cartesian line. On the MyCobot's constrained workspace, that line routinely passed through IK-infeasible configurations.

Result: planning returned False, the move was silently skipped, and the game continued as if the piece had moved.

Failure 02

Gripper control

The gripper topic was fire-and-forget with no delivery guarantee, so the workaround was to publish the same command 7+ times with sleep() between each.

Result: ~3s lost per actuation, and no confirmation the gripper ever actually closed before the arm moved on.

Failure 03

No lifecycle or recovery

main.py ran the game loop, node setup, user input, and HTTP calls in one blocking script. Vision was instantiated inside the controller behind a raw rospy.spin thread.

Result: any failure anywhere required killing and restarting the entire process.

The common root cause: the system was a Python call stack that happened to use ROS, not a distributed system. Every fix below is structural, not a patch.

Fix 01 · Motion planning

Cartesian straight lines → joint-space search

Why LIN failed

LIN interpolates the end-effector linearly through 3D space. MoveIt must solve IK at every intermediate waypoint. One infeasible point anywhere along the line kills the whole plan.

Why OMPL works

RRTConnect searches the 6-DOF joint configuration space directly, growing trees from both start and goal. The Cartesian path is unconstrained, so it can route around singularities and joint limits.

The trade-off we accepted

Motion no longer looks like a clean straight line to a human observer. For pick-and-place on a game board, reliability beats aesthetics.

This is a one-line change in arm_controller.py — but it is the change the whole rewrite was for. Every other fix exists to make sure that when a plan does fail, the system finds out about it.

Fix 02 & 03

Guaranteed delivery, and a system that can recover

Gripper reliability

The caller awaits the action result, so the arm physically cannot begin the next motion before the gripper has finished actuating.

Lifecycle & recovery

In ROS 1 a mid-game failure meant killing the process. Here game_manager can be deactivated, reconfigured with a new game, and reactivated without the motion stack ever restarting.

Both fixes share a shape: the original code guessed that something had happened and moved on. The rewrite makes the system wait for confirmation — from DDS for delivery, from the action result for completion, and from the lifecycle manager for readiness.

Fixes 02 & 03

Perception rewrite

Dropping the TF chain for a homography

What broke in ROS 1

ar_track_alvar needed accurate camera intrinsics, published poses in the camera frame, and depended on a camera → base_link TF transform that was never reliably established. Three stacked dependencies, each a failure point.

Why homography removes all three

Four markers at known board corners fully determine the projective transform. Camera tilt, height and angle are absorbed by the warp — no intrinsics file, no TF tree, no extrinsic calibration step.

Why HSV, not a learned model

Pieces are two solid colors on a flat board. Hue is lighting-invariant, detection is deterministic, it runs at frame rate on a Pi, and there is no training set to collect or domain shift to manage.

Status: the pipeline is implemented but the HSV bounds are still placeholders. Calibrating them against the real pieces under real lighting is the next perception task — they are exposed as ROS parameters specifically so that can be done without touching code.

What makes the graph work

Typed interfaces replace shared memory

In ROS 1, robotControl reached directly into an ARTagListener object and shared a mutable dict behind a lock. In ROS 2 every boundary is a compiled message contract — which means each node can be tested, replaced or restarted on its own.

InterfaceCarriesDirection
ExecuteMove.action game_id, move_string, current_position, new_position game_manager → robot_control
MoveArm.action x, y, z in metres, base frame robot_control → arm_controller
MoveGripper.action open (bool) robot_control → gripper_controller
GameState.msg position, available_moves, is_robot_turn, game_over game_manager → any subscriber
/vision/board_state occupancy string, one char per cell vision_node → robot_control

Why actions, not services or topics

Motion is long-running and can fail. Actions give the caller three things a topic cannot: a goal acknowledgement, streaming feedback, and a terminal result. A failed plan now propagates all the way back to the game loop instead of vanishing.

The async requirement

Calling spin_until_future_complete inside an action callback deadlocks under a MultiThreadedExecutor — the node is already being spun. The motion sequencer is therefore async throughout and awaits each goal, yielding the executor while it waits.

Game-agnostic by construction

The ROS 1 AR tracker was hardcoded for a single game. Adding a game here means one entry in centers.py and one in the _GAME_TYPES map — no node code changes.

The argument in one slide

What actually changed

Dimension ROS 1 (original) ROS 2 (rewrite)
Control flow One synchronous Python call stack Seven independent nodes over typed interfaces
Motion planning PILZ LIN — Cartesian, fails without a straight IK-feasible path OMPL RRTConnect — joint-space, IK required only at endpoints
Failure signalling plan() returns False; caller ignores it Action aborts propagate to the game loop and are logged
Gripper 7+ publishes with sleep(), no confirmation One RELIABLE publish, action result confirms actuation
Recovery Kill and restart the whole process Lifecycle transitions; per-node restart
Perception ar_track_alvar → TF tree → shared dict behind a lock ArUco homography → HSV → published board-state topic
Camera setup Intrinsics file + extrinsic TF calibration None — four corner markers fully determine the warp
Adding a game AR tracking hardcoded for one game Two table entries, no node changes
Concurrency threading.Thread(target=rospy.spin) MultiThreadedExecutor with async callbacks

The through-line: every failure in the original system traced back to the same decision — treating a distributed robotics problem as a single-threaded script. The rewrite does not patch those failures individually; it removes the structure that produced them.
